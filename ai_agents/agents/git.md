# Git Agent Definition

## Overview

The Git Agent is responsible for safely managing Git operations for the autonomous development workflow. It provides controlled capabilities for version control without allowing blind execution of arbitrary Git commands.

**Primary Model:** Qwen 3.5 (Text-Only)  
**Role:** Version Control Safety / Repository Management Agent  
**Boundaries:** Never executes arbitrary shell commands; only uses predefined safe operations

---

## Core Function: Controlled Git Operations

### When the Git Agent Operates

In the autonomous development workflow, the Git Agent operates after the Reviewer Agent approves code changes:

```
Reviewer → APPROVED → Git Agent
                    ↓
              Inspect Changes
              Create / Verify Branch
              Stage Approved Changes
              Create Commit
              Optional Push (if authorized)
              Git Result → Orchestrator
```

### Workflow Integration

The Git Agent integrates with:
- **Orchestrator**: Receives workflow direction and forwards Git results
- **Planner**: Preserves metadata (plan_id, milestone, task_id) in Git records
- **Reviewer**: Enforces approval gate before commits

---

## Responsibilities

The Git Agent must:

1. Inspect repository status
2. Identify current branch
3. Identify repository root
4. Inspect modified files
5. Inspect untracked files
6. Inspect staged files
7. Inspect unstaged changes
8. Inspect current diff
9. Inspect branch list
10. Inspect recent commit history
11. Detect merge conflicts
12. Detect detached HEAD state
13. Detect uncommitted changes
14. Create feature branches when authorized
15. Switch branches when authorized
16. Stage approved files
17. Unstage files
18. Create commits
19. Verify commit success
20. Push only when explicitly authorized
21. Verify remote synchronization
22. Detect push failures
23. Detect branch divergence
24. Detect non-fast-forward errors
25. Report Git operation results
26. Prevent unsafe Git operations

## Critical Git Safety Rules

### NEVER Blindly Execute Commands from Model Output

- Never run arbitrary shell commands generated by an LLM
- Never allow model-generated command injection
- Never automatically execute destructive Git operations

### DEFAULT PROHIBITED OPERATIONS (Require Explicit Authorization)

The following operations must be blocked by default and require explicit human authorization:

- `git reset --hard`
- `git clean -fd`
- `git clean -fdx`
- `git push --force`
- `git push --force-with-lease`
- `git branch -D`
- `git checkout .`
- `git restore .`
- `git restore --staged .`
- `git reflog delete`
- `git gc`
- Deleting branches
- Rewriting public history
- Changing remote URLs

### NEVER Automatically:

- Push without explicit authorization (`push_authorized = true`)
- Use force push automatically
- Perform destructive reset automatically
- Delete branches automatically
- Rewrite history automatically

The Git Agent should reject unsafe operations rather than attempting them.

---

## Operation Categories

### Read-Only Operations (Auto-performable)

These may be performed automatically without explicit workflow authorization:

- `status` - Inspect repository status
- `current_branch` - Get current branch name
- `branches` - List all branches
- `log` - Get recent commit history
- `diff` - Get unstaged diff
- `diff_staged` - Get staged diff
- `detect_conflicts` - Check for merge conflicts
- `remote_status` - Check remote synchronization

### Safe Write Operations (Require Workflow Authorization)

These require authorization from the Orchestrator workflow:

- `create_branch` - Create new feature branch
- `switch_branch` - Switch to another branch
- `stage_files` - Stage specific files for commit
- `unstage_files` - Unstage files from index
- `commit` - Create a commit

### Remote Operations (Require Explicit Authorization)

These require explicit user authorization:

- `push` - Push changes to remote
- `fetch` - Fetch from remote (requires auth)

The Git Agent must distinguish between:
- `operation_requested` - Someone asked for this operation
- `operation_authorized` - Operation is authorized (`authorization = true`)
- `operation_executed` - Operation was successfully executed

Never assume that a requested push is authorized.

## Reviewer Approval Gate

Before committing, the Git Agent must check Reviewer status:

```
Reviewer Status
├── APPROVED
│       ↓
│   Commit Allowed
│
├── APPROVED_WITH_WARNINGS
│       ↓
│   Commit Allowed if policy permits
│
├── REQUIRES_CHANGES
│       ↓
│   Commit Blocked
│
├── REJECTED
│       ↓
│   Commit Blocked
│
└── BLOCKED
↓
Commit Blocked
```

### Policy Rules:

- `approved` → commit allowed
- `approved_with_warnings` → commit allowed with warning
- `requires_changes` → commit denied
- `rejected` → commit denied
- `blocked` → commit denied

Allow this policy to be configurable.

---

## Stale Review Detection

Before committing, verify that code hasn't changed after approval:

```
Review Approved
↓
Code Changed
↓
Previous Review Invalid
↓
New Testing
↓
New Review
↓
Commit Allowed
```

If code changes after approval, the previous approval is stale. The Git Agent must require re-review before committing.

---

## Secret Detection

Before staging or committing, inspect candidate files for possible secrets:

### Detect patterns such as:

- API keys (e.g., `AKIA`, `sk_live_`, `pk_test_`)
- Access tokens (e.g., `Bearer eyJ...`)
- Passwords in code
- Private keys (PEM format)
- Connection strings with passwords
- JWT secrets
- Cloud credentials
- Database passwords

### If a likely secret is detected:

1. Block staging/commit
2. Redact the value (do not print it)
3. Report the affected file
4. Ask for human intervention

Never expose secret contents in logs or model prompts.

---

## Generated File Detection

Before committing, detect files that should not be committed by default:

- `.env` and environment files
- `node_modules/`
- `__pycache__/`
- `*.pyc`
- Build artifacts (e.g., `dist/`, `build/`)
- Log files (`.log`, `npm-debug.log`)
- OS files (`.DS_Store`, `Thumbs.db`)
- Temporary files (`.tmp`, `.temp`)

Respect `.gitignore`. Do not stage these automatically unless explicitly authorized.

---

## Commit Message Validation

The commit message should:

1. Be non-empty
2. Be meaningful
3. Describe the change
4. Follow project conventions where documented

### Conventional Commits Format (if project uses):

- `feat:` - New feature
- `fix:` - Bug fix
- `test:` - Test changes
- `docs:` - Documentation changes
- `style:` - Code style changes
- `refactor:` - Code refactoring
- `perf:` - Performance improvements
- `chore:` - Maintenance tasks

### Reject Meaningless Messages:

Unless explicitly authorized, reject:
- `update`
- `changes`
- `fix`
- `test`
- `stuff`

---

## Push Authorization Workflow

Push must be treated as a separate operation from commit.

Default workflow:

```
Code → Review Approved → Commit → Push Authorization → Push → Verify Remote
```

The Git Agent must NOT automatically push unless:

1. `push_authorized = true`
2. Repository is valid
3. Branch is valid
4. Commit exists
5. No unresolved conflicts exist
6. No unsafe state exists

Never use force push automatically.

If push fails due to:
- non-fast-forward
- authentication
- network
- branch protection
- remote rejection

Return a structured failure. Do not automatically force push.

---

## Branch Management

### Branch Creation Rules:

1. Verify repository exists
2. Verify current state is clean (or changes are staged)
3. Verify base branch exists and is known
4. Verify branch does not already exist
5. Create branch
6. Verify current branch switched correctly
7. Return structured result

### Do NOT automatically:

- Delete old branches
- Rename branches
- Force checkout over uncommitted changes

---

## Branch Naming Strategy

Use a predictable branch naming strategy:

- `feature/milestone-X-Y-description` (e.g., `feature/milestone-6-6-workspace`)
- `fix/component-name-issue` (e.g., `fix/project-api-serialization`)
- `bugfix/description` (e.g., `bugfix/login-validation`)
- `hotfix/critical-fix`

Validate branch names before creating them. Reject unsafe or invalid names.

---

## Change Inspection

Before staging or committing, the Git Agent must inspect:

1. Git status
2. Changed files
3. Untracked files
4. Staged files
5. Unstaged diff

The Git Agent must detect:

- Unexpected files (outside of known change scope)
- Generated files (build outputs)
- Secrets
- `.env` files
- Large binaries
- Build artifacts (`dist/`, `build/`)
- `node_modules/`
- Python virtual environments (`.venv/`)
- Cache files (`.cache/`)
- Temporary files

---

## Merge Conflict Detection

The Git Agent must detect:

1. Unmerged paths
2. Conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`)
3. Merge/rebase state
4. Cherry-pick state

If conflicts exist:

1. Block commit
2. Block push
3. Return structured conflict information
4. Identify affected files
5. Escalate to Orchestrator

The Git Agent must NOT automatically resolve conflicts. Conflict resolution will be handled by a future controlled workflow or human intervention.

---

## Repository State Validation

Before write operations, verify:

1. Repository exists (`.git` directory present)
2. Repository is valid (not corrupted)
3. Current branch is known
4. HEAD is valid (not detached unless intentional)
5. No unresolved merge conflicts
6. Repository is not in an unsafe operation state (e.g., rebase in progress)
7. Requested files exist
8. Requested files belong to repository
9. Files are not outside repository boundaries

Reject path traversal attempts. Do not allow operations on arbitrary filesystem locations.

## Input Schema

The Git Agent accepts structured input with the following fields:

```json
{
  "git_request_id": "GIT-001",
  "operation": "commit",
  "repository_path": "D:/Sanskriti_AI_Studio",
  "branch_name": "feature/milestone-6-6-workspace",
  "base_branch": "main",
  "files": ["frontend/src/pages/Workspace.tsx"],
  "commit_message": "feat: implement project workspace dashboard",
  "remote": "origin",
  "push_authorized": false,
  "reviewer_status": "approved",
  "review_request_id": "REVIEW-001",
  "plan_id": "PLAN-6.6-001",
  "milestone": "6.6",
  "task_id": "TASK-001",
  "requested_by": "orchestrator",
  "authorization_context": {
    "workflow_step": "post-review-commit",
    "human_approved": false
  }
}
```

### Field Descriptions:

| Field | Description | Required |
|-------|-------------|----------|
| `git_request_id` | Unique identifier for this Git operation request | Yes |
| `operation` | Type of Git operation (e.g., `commit`, `branch`) | Yes |
| `repository_path` | Path to the Git repository root | Yes |
| `branch_name` | Target branch name (for create/switch) | Context-dependent |
| `base_branch` | Base branch for new branches | Context-dependent |
| `files` | List of files to operate on | Context-dependent |
| `commit_message` | Commit message for commit operation | For commits |
| `remote` | Remote repository name (for push/fetch) | Context-dependent |
| `push_authorized` | Whether push is authorized | For push operations |
| `reviewer_status` | Result of Reviewer Agent (`approved`, `requires_changes`, etc.) | For commits |
| `review_request_id` | Reference to review request | Context-dependent |
| `plan_id` | Planner task plan reference | Context-dependent |
| `milestone` | Current milestone identifier | Context-dependent |
| `task_id` | Task identifier | Context-dependent |
| `requested_by` | Who requested this operation (`orchestrator`, `user`, etc.) | Yes |
| `authorization_context` | Additional authorization information | Optional |

## Output Schema

The Git Agent returns structured results:

```json
{
  "git_request_id": "GIT-001",
  "operation": "commit",
  "status": "success",
  "repository_path": "D:/Sanskriti_AI_Studio",
  "current_branch": "feature/milestone-6-6-workspace",
  "target_branch": null,
  "changed_files": ["frontend/src/pages/Workspace.tsx"],
  "staged_files": ["frontend/src/pages/Workspace.tsx"],
  "commit_hash": "abc123def456",
  "commit_message": "feat: implement project workspace dashboard",
  "remote": "origin",
  "push_status": null,
  "reviewer_status": "approved",
  "authorization_status": "authorized",
  "safety_checks": {
    "secrets_detected": false,
    "conflicts_detected": false,
    "unexpected_files": false,
    "generated_files_detected": false
  },
  "warnings": [],
  "errors": []
}
```

### Status Values:

| Value | Description |
|-------|-------------|
| `success` | Operation completed successfully |
| `blocked` | Operation was blocked by safety rules |
| `failed` | Operation failed due to an error |
| `not_applicable` | Operation not applicable to current state |
| `requires_changes` | Review requires changes (commit blocked) |

## Security Requirements

The Git Agent must:

- Never expose secrets
- Never expose private keys
- Never log credentials
- Never include `.env` contents in prompts
- Never allow arbitrary shell execution
- Never allow command injection
- Never force push automatically
- Never perform destructive reset automatically
- Never delete branches automatically
- Never rewrite history automatically

All Git operations must operate within the configured repository root.

---

## LM Studio / Qwen 3.5 Requirements

The Git Agent may use Qwen 3.5 only for reasoning or classification where necessary:

1. Do not use the LLM to generate raw shell commands that are executed blindly
2. Prefer structured operations (e.g., `{"operation": "commit", "files": ["file1"], "message": "..."}`)
3. The runtime translates structured operations into safe, predefined Git commands
4. Never send images to Qwen 3.5
5. Keep prompts focused and minimal

---

## Git Bash Compatibility

All user-facing Git workflow documentation and examples must use Git Bash commands:

```bash
git status
git branch
git diff
git add path/to/file
git commit -m "feat: implement workspace dashboard"
git push origin feature/milestone-6-6-workspace
```

Do not provide PowerShell or CMD-specific syntax.

---

## Documentation Updates

The Git Agent should update documentation only through the existing Documentation Agent workflow.

The Git Agent itself should not directly modify project documentation unless the task explicitly belongs to Git documentation.

The Git Agent records:

1. Commit hash in state
2. Branch information in state
3. Files changed in state
4. Operation result in state

## Testing Strategy

### Unit Tests (Test File: `ai_agents/tests/test_git_agent.py`)

At minimum test:

1. Repository status detection
2. Current branch detection
3. Branch listing
4. Diff inspection (staged/unstaged)
5. Branch creation/validation/switching
6. Uncommitted change detection
7. Conflict detection
8. Secret detection
9. Generated file detection
10. Reviewer approval validation
11. Stale review detection
12. File staging/unstaging
13. Commit message validation
14. Commit creation and verification
15. Push authorization enforcement
16. Force push rejection
17. Destructive command rejection
18. Path traversal prevention
19. Invalid repository handling
20. Non-fast-forward handling
21. Remote failure handling
22. Invalid operation handling
23. Structured output validation

Use a temporary test repository for Git integration tests. Do not use the real project repository for destructive tests.

### Integration Tests

Test these scenarios:

1. **Scenario A — Successful Commit**: Reviewer APPROVED → Git Agent Inspect → Stage → Commit → Verify Commit
2. **Scenario B — Review Not Approved**: Reviewer REQUIRES_CHANGES → Git Agent blocks commit
3. **Scenario C — Code Changed After Review**: Review Approved → Code Modified → Stale Approval Detected → Commit Blocked
4. **Scenario D — Secret Detected**: File contains secret → Secret Detection → Commit Blocked (secret value never printed)
5. **Scenario E — Merge Conflict**: Repository has conflict → Git Agent blocks commit and push → Orchestrator escalation
6. **Scenario F — Push Authorization**: Commit succeeds → Push Not Authorized → Blocked; then Push Authorized → Push Succeeds
